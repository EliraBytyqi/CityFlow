## 1. Problem Statement
Cities around the world frequently modify road networks—closing streets for construction, pedestrianizing urban centers, or altering traffic flow during major events. However, traditional urban planning relies on static traffic counts. Counting how many vehicles pass down a street today **does not tell you where those vehicles will go tomorrow when the street is closed**.

Unintended traffic redistribution leads to severe bottlenecking, delayed emergency response times, gridlock on residential side streets, and unexpected economic disruption.

---

## 2. The CityFlow AI Solution
**CityFlow AI** connects live road-camera feeds to vehicle detection and traffic planning. Choose a camera to watch its live stream with YOLO detections drawn on the video; the backend also records periodic counts for analytics and traffic-closure scenarios.

When an urban planner selects a road and specifies a closure percentage (25%, 50%, 75%, or 100%), CityFlow AI:
1. Calculates displaced traffic volume based on time of day.
2. Identifies viable alternative routes across the directed street graph using NetworkX.
3. Redistributes flow based on route capacity, current utilization, and travel time.
4. Calculates updated speed reductions, bottleneck locations, and estimated travel delays.
5. Summarizes the modeled network trade-offs.

---

## 3. Existing AI Model Integration

The Cameras page starts the bundled Ultralytics YOLO model on the selected live camera feed. The backend reads the HLS stream with OpenCV/FFmpeg, draws vehicle boxes on each processed frame, and serves those annotated frames to the frontend as MJPEG. It also saves a detection count at most once every 30 seconds through the ingestion adapter. Only one camera inference worker runs at a time; selecting another camera switches the worker.

The model weights file `yolo11m.pt` must be in the repository root (the default checkout includes it). Inference can be demanding on CPU; a supported GPU can improve throughput. `traffic_counter.py` and `detect_cars.py` are standalone utilities; the live Cameras page uses the backend inference service.

### Ingestion Adapter (`TrafficModelAdapter`)
Located in `backend/app/services/traffic_ingestion.py`.

CityFlow AI accepts observations in two standard formats from the existing AI model:

#### 1. Single Detection Ingestion:
`POST /api/traffic/ingest/detection`
```json
{
  "camera_id": "CAM_01",
  "timestamp": "2026-10-03T08:15:00",
  "cars": 82,
  "trucks": 7,
  "buses": 3,
  "motorcycles": 5,
  "total": 97
}
```

#### 2. Aggregated Count Ingestion:
`POST /api/traffic/ingest/count`
```json
{
  "camera_id": "CAM_01",
  "date": "2026-10-03",
  "hour": 8,
  "vehicle_count": 1240
}
```

## 4. Data Source Distinction

To maintain completely transparent decision support, every metric in CityFlow AI carries an explicit data source label:

* **`[OBSERVED]`** — Counts produced by the live YOLO worker or received through the traffic ingestion API.
* **`[ESTIMATED]`** — Quantities mathematically calculated from raw observations (e.g., average hourly speed, daily capacity utilization).
* **`[SIMULATED]`** — Hypothetical scenario outputs generated by the traffic redistribution engine.
* **`[DEMO DATA]`** — Deterministic synthetic baseline data used before live observations are available.

---

## 5. Traffic Simulation Methodology

CityFlow AI models the city street network as a weighted directed graph $G = (V, E)$ using **NetworkX**:
* **Nodes ($V$)**: City intersections (signalized, roundabouts, uncontrolled).
* **Edges ($E$)**: Directed road segments defined by capacity ($C$), free-flow speed ($S$), length ($L$), and current flow ($F$).

### Congestion & Delay Modeling
Utilization ($U$) is defined as:
$$U = \frac{\text{Flow}}{\text{Capacity}}$$

Congestion classification:
* $U < 0.50$: **LOW** (Green)
* $0.50 \le U < 0.75$: **MODERATE** (Yellow)
* $0.75 \le U < 0.90$: **HIGH** (Orange)
* $U \ge 0.90$: **CRITICAL** (Red)

Travel speeds are estimated using a Bureau of Public Roads (BPR) impedance function:
$$\text{Speed} = \frac{S}{1 + \alpha \cdot U^\beta} \quad (\alpha = 0.15, \beta = 4.0)$$

When a road closure is executed, displaced traffic is rerouted along $k$-shortest paths weighted by path travel times and available capacity on surrounding links.

## 7. Installation & Running Locally

### Step 1: Install backend dependencies and start the API

From the repository root, create and activate a virtual environment (Windows PowerShell shown):

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
```

On macOS/Linux, activate it with `source .venv/bin/activate` instead. Then:

```bash
cd backend
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload --port 8000
```
* Backend API running at: `http://localhost:8000`
* Interactive API Docs (Swagger): `http://localhost:8000/docs`
* Keep this terminal open. On startup, the backend initializes its SQLite database and syncs configured camera names and stream URLs.

The model weights are expected at `yolo11m.pt` in the repository root. The backend needs outbound internet access to read configured HLS camera feeds.

### Step 2: Start Frontend Dev Server
In a new terminal window:
```bash
cd frontend
npm install
npm run dev
```
* Frontend running at: `http://localhost:5173`
* The frontend uses `http://localhost:8000` by default. Override it with `VITE_API_URL` (for example in `frontend/.env.local`).

For a second computer on the same network, bind the backend to the LAN interface with `python -m uvicorn app.main:app --host 0.0.0.0 --port 8000`, start Vite with `npm run dev -- --host 0.0.0.0`, and set that frontend's `VITE_API_URL` to the backend computer's reachable IP and port. The backend computer needs access to the camera streams. Configure backend CORS for the frontend host if the browser reports a CORS error.

## 8. View a live camera and detections

1. Start the backend and frontend as described above.
2. Open the Cameras page and select a location.
3. Wait for inference to report live. The video panel shows annotated frames and current vehicle counts.

The first selection loads `yolo11m.pt` and opens that location's HLS feed, so startup can take a little time. On failure, the page displays the backend error; check the backend terminal for model, stream, or FFmpeg details. The configured locations are Fushë Kosovë, Ulpianë, Bregu i Diellit, Pejton, Magjistralja Vushtrri–Mitrovicë, Ortakoll: Wesley Clark, Prizren, Veternik 2, Veternik 1, Rr. Tirana, Prizren, Deçan, and Rrethi i Çagllavicës.

Camera names and HLS URLs are configured in `backend/app/demo_data.py`; backend startup syncs them into the local database. Inference is hosted by the backend process, so the UI must connect to that same backend.

## 9. Key Pages & Features

1. **Dashboard (`/`)**: City network overview, key traffic indicators, and road-closure impact exploration.
2. **Traffic Analytics (`/analytics`)**: Hourly volume and vehicle-class breakdowns with data-source context.
3. **Scenarios (`/scenarios`)**: Compare modeled outcomes for multiple road-closure levels.
4. **Cameras (`/cameras`)**: Select a configured live feed, view annotated YOLO frames and detections, and review hourly volume history.
